## Prompt para Figma Make

Rediseñá mi página actual de **gestión de talleres mecánicos** tomando como base la interfaz existente de la captura. Quiero que analices la UX/UI actual y realices directamente todos los cambios necesarios para mejorar el flujo, la jerarquía visual, la consistencia de formularios y la organización general del sistema.

No consultes demasiado. Tomá decisiones razonables de UX/UI cuando haga falta. Consultá solo si hay un dato crítico imposible de resolver con la información actual. **No inventes campos nuevos ni funcionalidades innecesarias.** Usá los campos y secciones actuales del sistema, reorganizándolos de forma más clara.

Mantené la identidad visual general actual: sidebar lateral, estética limpia, tonos grises, tarjetas blancas, bordes suaves, formularios claros y color principal violeta/azulado.

# Objetivo general del rediseño

El sistema debe reorganizarse para que la **Orden de Trabajo** sea el eje principal.

Las secciones de:

* Clientes
* Presupuestos
* Órdenes de Trabajo
* Dashboard
* Calendario / Agenda

deben girar alrededor de la OT.

La lógica principal del sistema debe ser:

**Cliente → Vehículo → Orden de Trabajo → Presupuesto**

El presupuesto no debe funcionar como un módulo independiente. Siempre debe depender de una OT.

---

# 1. Acción principal del sistema

La acción más importante debe ser:

**+ Ingresar nueva OT**

Esta acción debe estar visible en dos lugares:

1. En el menú lateral.
2. En el dashboard, como acceso rápido principal y temprano.

Como crear una OT es la acción central del sistema, no debe quedar escondida ni depender de navegar por varias secciones.

---

# 2. Flujo para crear una nueva OT

La creación de una nueva Orden de Trabajo debe empezar siempre por la búsqueda de patente.

Flujo:

1. El usuario hace clic en **+ Ingresar nueva OT**.
2. Se abre una pantalla principal de creación de OT.
3. El primer paso es ingresar la patente del vehículo.
4. El campo debe tener un texto claro:
   **Ingresar patente sin espacios**
5. Usar placeholder:
   **Ej: AA123BB**
6. Botón principal:
   **Buscar patente**
7. El sistema debe chequear si esa patente pertenece a un vehículo o cliente existente.

---

# 3. Caso: patente existente

Si la patente ya está registrada:

Mostrar una card clara con el título:

**Vehículo encontrado**

La card debe mostrar los datos disponibles del vehículo y del cliente asociado, sin pedir que el usuario cargue nuevamente información ya existente.

Mostrar, si existen en el sistema actual:

* Patente
* Marca
* Modelo
* Cliente asociado
* Teléfono o dato principal del cliente
* Historial de OTs, si está disponible

Acción principal:

**Crear nueva OT para este vehículo**

Al hacer clic, dirigir directamente a una nueva Orden de Trabajo con los datos del vehículo y del cliente ya cargados.

Acción secundaria:

**Ver historial de órdenes**

Esta acción debe tener menor jerarquía visual que la acción principal.

---

# 4. Caso: patente inexistente

Si la patente no está registrada:

No usar un modal genérico con botón “Aceptar”.

Reemplazarlo por una card o modal claro, con mejor microcopy.

Título:

**Vehículo no encontrado**

Texto:

**No encontramos un vehículo registrado con esta patente. Podés cargarlo ahora para continuar con la nueva Orden de Trabajo.**

Acciones:

* Botón principal: **Continuar con alta de vehículo y cliente**
* Botón secundario: **Volver a buscar**

Al continuar, llevar al formulario de nueva OT permitiendo cargar los datos del vehículo y del cliente.

---

# 5. Orden de Trabajo como eje principal

La Orden de Trabajo debe concentrar toda la información importante del proceso del taller.

Dentro de una OT deben estar integrados:

* Datos del vehículo.
* Datos del cliente.
* Datos de la orden.
* Servicio solicitado.
* Estado de la OT.
* Presupuesto asociado.
* Repuestos o ítems incluidos, si ya existen actualmente en el sistema.
* Totales y condiciones existentes, si ya forman parte del sistema.
* Fechas importantes asociadas a calendario, si corresponde.

La pantalla de OT debe sentirse como el lugar principal de trabajo del usuario.

Organizar la OT con bloques, pestañas o secciones internas:

1. **Vehículo**
2. **Cliente**
3. **Trabajo / Servicio**
4. **Presupuesto**
5. **Estado y seguimiento**
6. **Agenda / Fechas asociadas**, si corresponde

Usar esta estructura como organización visual. No agregar funcionalidades nuevas innecesarias.

---

# 6. Regla obligatoria para Presupuestos

A partir de este rediseño, **ningún presupuesto puede existir de forma independiente**.

Todo presupuesto debe estar siempre asociado a una Orden de Trabajo.

Reglas:

* No se puede crear un presupuesto sin una OT asociada.
* No debe existir un botón principal de **Nuevo presupuesto** fuera de una OT.
* La acción correcta debe ser:
  **Crear presupuesto para esta OT**
* La edición del presupuesto debe hacerse dentro de la Orden de Trabajo.
* El presupuesto debe vivir dentro de la OT como una pestaña, bloque o sección interna.
* Si se mantiene la sección **Presupuestos** en el menú lateral, debe funcionar solo como vista de consulta o listado.
* Al abrir un presupuesto desde ese listado, el usuario debe ser dirigido a la Orden de Trabajo correspondiente, específicamente al bloque o pestaña de Presupuesto.

El flujo debe quedar claro:

**Cliente → Vehículo → Orden de Trabajo → Presupuesto**

No deben existir módulos separados que compitan entre sí.

---

# 7. Sección Presupuestos

Replantear completamente la sección Presupuestos para que no funcione como un flujo independiente.

Si queda en el menú lateral, debe funcionar como:

* Listado de presupuestos existentes.
* Vista de consulta.
* Acceso rápido a la OT relacionada.
* Filtros o estados solo si ya existen actualmente en el sistema.

No permitir crear presupuestos sueltos desde esta sección.

Cambiar microcopy:

En lugar de:

**Nuevo presupuesto**

Usar:

**Crear presupuesto para esta OT**

En lugar de:

**Ver presupuesto**

Usar:

**Ver presupuesto asociado a la OT**

En lugar de:

**Presupuesto sin asignar**

Usar:

**Esta OT todavía no tiene presupuesto**

Eliminar cualquier opción de:

**Crear presupuesto independiente**

---

# 8. Sección Clientes

La sección Clientes debe pasar a ser secundaria respecto de la Orden de Trabajo.

Debe funcionar como una base de consulta y gestión.

Debe permitir:

* Ver listado de clientes.
* Ver datos principales del cliente.
* Ver vehículos asociados.
* Ver órdenes de trabajo vinculadas a ese cliente.
* Crear una nueva OT desde un cliente existente.

Acción sugerida:

**Crear nueva OT para este cliente**

Si el cliente ya existe, sus datos deben poder reutilizarse en una nueva OT.

Evitar que el usuario tenga que cargar dos veces la misma información.

# 10. Consistencia visual de formularios

Unificar visualmente todos los formularios del sistema.

Actualmente los inputs, selects, botones y bloques tienen tamaños y alineaciones poco consistentes. Rediseñar la interfaz para que el usuario se familiarice rápidamente con el patrón visual.

Aplicar estas reglas:

* Todos los inputs deben tener la misma altura.
* Todos los selects deben tener la misma altura que los inputs.
* Los labels deben estar siempre ubicados de la misma forma.
* Los campos obligatorios deben marcarse de manera consistente.
* Los mensajes de ayuda y error deben aparecer siempre debajo del campo correspondiente.
* Los botones principales deben tener el mismo tamaño, color y jerarquía.
* Los botones secundarios deben diferenciarse claramente de los principales.
* Usar cards o bloques visuales para separar Vehículo, Cliente, OT y Presupuesto.
* Mantener márgenes y espaciados constantes.
* Alinear los campos en una grilla clara.
* Evitar campos sueltos con anchos diferentes sin motivo.
* Reducir la sensación de formulario largo y pesado.
* Usar secciones plegables, tabs o pasos si mejora la claridad.
* Mantener visible el contexto de la OT mientras el usuario carga datos.
* Mejorar los estados vacíos, errores y confirmaciones.
* Reemplazar mensajes genéricos por textos accionables y específicos.

# 11. Dashboard principal

Rediseñar el dashboard para que funcione como una **pantalla de inicio operativa del taller**, no solo como una vista estadística.

Como la acción principal del sistema es la creación de una Orden de Trabajo, el dashboard debe incluir un acceso rápido, visible y temprano para:

**+ Crear nueva OT**

Este acceso debe estar en una zona prioritaria del dashboard, idealmente en la parte superior o en una card destacada.

El dashboard debe responder rápidamente:

* ¿Qué tengo que hacer ahora?
* ¿Qué autos están en proceso?
* ¿Qué turnos tengo hoy?
* ¿Qué presupuestos necesitan acción?
* ¿Qué OTs requieren atención?
* ¿Dónde creo una nueva OT sin perder tiempo?

---

# 12. Calendario integrado con Google Calendar

Incluir un módulo de **Calendario / Agenda** asociado a Google Calendar.

El calendario debe formar parte del sistema de gestión del taller y debe estar conectado visualmente con las Órdenes de Trabajo, turnos y recordatorios.

No diseñarlo como una sección aislada. El calendario debe ayudar al usuario a organizar:

* Turnos de ingreso de vehículos.
* Fechas de entrega.
* Recordatorios importantes.
* Trabajos programados.
* Seguimiento de OTs activas.
* Citas asociadas a clientes o vehículos.

El calendario debe estar integrado al flujo principal del sistema, especialmente a la Orden de Trabajo.

---

Agregar acceso al calendario en dos lugares:

### 1. Dashboard principal

El dashboard debe incluir una vista resumida del calendario:

**Agenda de hoy**

o

**Próximos turnos**

Este bloque debe mostrar próximos eventos importantes del taller, con acciones rápidas para ver o crear OTs.

### 2. Menú lateral

**Calendario**

o

# 13. Vista completa del calendario

Diseñar una pantalla de calendario con vistas:

* Día
* Semana
* Mes

La vista más importante para un taller debería ser **Día** o **Semana**, porque permite ver la carga operativa real.

Cada evento del calendario debe mostrar:

* Hora
* Cliente
* Patente
* Servicio
* Estado
* Si tiene OT asociada o no

Cuando un evento del calendario está asociado a una Orden de Trabajo, debe mostrar una acción clara:

**Ver OT**

Si el evento todavía no tiene OT asociada, debe mostrar:

**Crear OT desde este turno**

Al crear una OT desde un evento del calendario, reutilizar los datos ya cargados del turno, como cliente, patente, fecha, hora y servicio, si están disponibles.

El flujo debe respetar la lógica principal del sistema:

**Turno / Evento → Patente → Cliente / Vehículo → Orden de Trabajo**

No crear presupuestos desde el calendario. El presupuesto solo puede crearse dentro de una OT.

# 16. Criterios visuales generales

La interfaz debe sentirse profesional, clara y práctica para usuarios de taller.

Priorizar:

* Rapidez para crear una OT.
* Menos pasos innecesarios.
* Menos carga visual.
* Jerarquía clara.
* Formularios ordenados.
* Acciones específicas.
* Microcopy claro.
* Componentes reutilizables.
* Tamaños consistentes.
* Mejor escaneabilidad.
* Menos modales genéricos.
* Más continuidad entre Cliente, Vehículo, OT, Presupuesto y Calendario.
* Dashboard operativo, no decorativo.
* Calendario como herramienta de trabajo, no como agenda aislada.

No cambiar todo el estilo visual desde cero. Mejorar la interfaz actual manteniendo su base.
